# TUTOR 후속 질문 — 설계

이슈: [#19](https://github.com/picpal/dev-crew/issues/19) · [TUTOR 학습 Agent 설계](./2026-08-21-tutor-agent-design.md)의 후속.

## 목적

**채점과 해설을 보고도 이해가 안 가는 부분을 그 자리에서 더 파고들 수 있게 한다.**

지금 tutor는 회차를 채점하고 리포트 링크를 주는 데서 끝난다. 해설이 짧거나 전제가 낯설면
학습자는 거기서 막히고, 물어볼 곳이 없다. 회차 스레드에서 이어 물을 수 있으면 그 막힘이
풀린다 — 회차의 문항·정답·근거가 이미 그 스레드의 맥락이므로, 질문은 짧아도 성립한다.

이 기능의 성패는 **깊이**에 있다. 해설을 다시 읽어 주는 수준이면 존재 이유가 없다. 그래서
답변 에이전트는 저장된 해설에 갇히지 않고 **repo를 직접 읽는다.**

## 역할과 provider

| Role | provider/tier | 책임 |
|---|---|---|
| `TUTOR_TA` | `DEFAULT` (Claude sonnet-5, HIGH) | 회차 문항에 대한 후속 질문 답변. 읽기 도구로 repo를 직접 확인 |

출제(`HIGH_CAPABILITY`)보다 한 단계 낮게 잡는다. 질문은 **정답·근거·해설이 이미 주어진
상태에서 시작**하므로 백지에서 출제하는 것보다 쉬운 과업이고, 대화는 리듬이 중요하다.
부족하면 tier만 올린다.

`TUTOR`/`TUTOR_VERIFIER`와 달리 provider를 가르지 않는다. 교차 검증이 아니라 설명이고,
검증은 인용 대조(결정적)가 맡는다.

## 경계

### 언제 받는가 — 채점 후에만

**진행 중인 회차에서는 자유 답글을 받지 않는다.** 지금과 같이 무시하되, 안내는 보낸다:

> ⚠️ 회차가 진행 중입니다 — 채점이 끝난 뒤에 물어봐 주세요.

**안내는 회차당 한 번만 보낸다.** 답글마다 매번 보내면 채널이 시끄러워지고, 두 번째부터는
알려주는 것이 아니라 잔소리다. 한 번 안내한 스레드는 표시해 두고 이후 답글은 조용히 버린다.

이유는 tutor의 핵심 원칙이다: *진행 중에는 정답을 공개하지 않는다.* 문항마다 정오를
알려주면 마지막 리포트가 할 일이 없어지고, 학습자는 문항이 아니라 피드백을 좇는다
([2026-08-21 설계](./2026-08-21-tutor-agent-design.md)의 Slack 흐름).

질문을 받으면 그 원칙을 우회하는 경로가 생긴다 — "3번 보기 B가 왜 틀려?"는 형식상 질문이지만
답하는 순간 정답이 새어 나간다. 미답변 문항의 정답·해설을 컨텍스트에서 기계적으로 빼는
방법도 있으나, 조립 로직과 그 회귀 테스트가 기능 본체보다 커진다. **채점 후로 제한하면
유출 경로가 구조적으로 사라지고, 사용자의 실제 의도("해설을 보고도 모르겠는 것")와도
정확히 겹친다.**

프롬프트로 "정답을 말하지 마라"라고 막는 방법은 쓰지 않는다. 이 저장소는 role 경계를
prompt가 아니라 harness가 강제한다.

### 누가 물을 수 있는가 — 회차 owner만

회차를 시작한 사람만 질문할 수 있다. 기존 `NOT_OWNER`("남이 회차의 답을 대신 누르지
못한다")와 **같은 축**이다 — 회차는 그것을 시작한 사람의 것이고, 그 사람의 대화 세션으로
돈다. 남이 물으면 owner가 이어 갈 맥락이 남의 질문으로 채워진다.

**스포일러 차단이 이 게이트의 근거다.** 답변에는 회차의 답안지가 그대로 들어 있고,
회차는 스레드 안에서만 돈다 — 채널 피드로 새지 않는다. 한때 `reply_broadcast`로 채널에도
게시했으나, 그러면 게이트가 "누가 묻는가"만 막고 "누가 보는가"는 못 막아 근거 자체가
무너졌다. 2026-08-24 사용자 결정으로 broadcast를 철회했다 — 스레드 답글은 PC·모바일 모두
스레드 안에서 보이므로, broadcast가 사던 것은 "한 탭 덜 하기"뿐이었다.

> 트레이드오프: 스레드 답글은 모바일 채널 피드에 뜨지 않아 회차가 통째로 보이지 않았고
> (2026-08-24), 그래서 게시 범위를 채널로 넓히는 쪽을 택했다 — 같은 채널의 다른 학습자에게
> 해설이 함께 노출되는 것은 그 대가로 감수한 것이다.

그리고 게이트는 **fail-closed**다: `owner`가 비어 있으면(필드가 없던 옛 회차, 손상된
페이로드) 통과가 아니라 거절이다.

### 언제까지 — 회차 TTL(24시간)

`ROUND_TTL`을 그대로 쓴다. 하루가 지나면 코드도 기억도 달라지므로, 그때의 근거로 답하는 것이
오히려 틀린 설명이 된다.

> ⚠️ 이 회차는 하루가 지나 이어서 물을 수 없습니다. `@tutor <repo명>:` 로 다시 시작해 주세요.

**메모리 세션이 살아 있어도 같은 규칙을 쓴다.** 지금 TTL 검사는 trace 복원 경로에만 있어서,
프로세스가 계속 떠 있으면 하루가 지난 회차도 그대로 통과한다. 세션이 자기 시작 시각을 들고
있어야 두 경로가 같은 규칙을 따른다.

### 동시성 — 스레드당 1턴

`asyncio.Lock`으로 직렬화한다. lock이 잡혀 있으면 그렇다고 말한다 — 말해 주지 않으면
무반응으로 보이고 사용자는 질문을 반복한다 (2026-08-24 실사고, lessons C14).

### 도구 — 읽기 전용, cwd는 그 repo

`_READ_TOOLS`(`Read`/`Grep`/`Glob`)만. `TUTOR`와 동일한 격리다. 쓰기는 없다.

## 세션 모델 — 유지하되 trace에 남긴다

후속 질문은 이어져야 한다. "그럼 그건 왜?"가 통하지 않으면 파고드는 도구가 아니다. 그래서
스레드당 **세션 하나**를 유지하고, 질문은 같은 세션의 다음 turn으로 보낸다.

`start_worker(conversational=True)`는 쓰지 않는다. 그 스위치가 하는 일은 **output_schema
주입을 생략하는 것 하나뿐**이고, 스키마 없이 뜬 세션은 `structured_output`을 절대 내지
않는다 — 매 turn이 스키마 제출인 이 role에서는 모든 질문이 "빈 답변"으로 실패한다.
세션이 turn을 넘어 유지되는 것은 이 스위치와 무관하다.

### 세션 반납 — 유휴 TTL과 상한

스레드당 살아 있는 워커 프로세스 하나를 두는 설계이므로 반납은 선택이 아니다.
`slack_brain`과 같은 규칙을 쓴다: 마지막 질문 뒤 `TA_IDLE_TTL`(6시간) 방치되면 반납하고,
`MAX_TA_SESSIONS`(50)를 넘으면 가장 오래 방치된 회차부터 축출한다. **회차 TTL 만료를
감지한 자리에서도 반납한다** — "이 회차는 못 쓴다"고 말하면서 그 워커를 살려 두면 반납
경로가 없는 것과 같다. 답변 중인 회차는 건드리지 않는다.

동시에 **모든 Q&A를 trace에 남긴다.** 이 저장소에서 회차의 진실은 메모리 세션이 아니라
trace다 (`slack_tutor.py` 첫머리). 세션은 프로세스와 함께 사라지지만 trace는 남는다.

### 재시작 시 — 회차 맥락으로 새 세션, 과거 Q&A는 되살리지 않는다

메모리 세션이 없으면 trace의 `QuizIssuedEvent` + `QuizGradedEvent`로 회차를 복원해 **새
대화형 세션을 연다.** 과거 질문·답변은 세션에 replay하지 **않는다.**

의도적인 제외다. 회차 컨텍스트(문항·정답·근거·해설·사용자의 답)만으로도 후속 질문은
성립하고, 재시작은 드물다. replay를 넣는 순간 "무엇을 얼마나 되살리나 / 토큰 예산은 /
요약할 것인가"가 통째로 딸려 온다. 필요해지면 그때 별도로 다룬다.

## 컨텍스트와 신뢰 경계

### 세션 시작 시 1회 주입

| 항목 | 내용 |
|---|---|
| 회차 문항 | 10문항 전체 — 지문·보기·**정답**·evidence(경로/줄/원문)·해설 |
| 채점 결과 | 사용자가 고른 답과 정오. **틀린 문항을 먼저 놓는다** — 질문은 거기서 나온다 |
| repo | 경로만. 나머지는 에이전트가 읽기 도구로 직접 찾는다 |

### 사용자 질문은 untrusted다

`untrusted.fence()` / `NOTE`로 감싸 넘긴다. 회차 컨텍스트(하네스가 만든 것)와 사용자 입력이
경계 표시 없이 이어붙으면 lessons C6이 지적한 자리가 된다.

## 답변

### 출력 스키마

```
status      roles.STATUS_ENUM 전체 (PASS | NOT_PASS | NEED_REPLAN | BLOCKED |
                                    INSUFFICIENT_CAPABILITY)
summary     한 줄 요약
answer      Slack mrkdwn 본문
citations   [{path, start_line, end_line, quote}] — 선택
```

`status`의 enum과 `summary`는 **줄일 수 없다.** `roles.load_bundle`이 모든 role 번들에
공통 골격(`status` enum 일치, `summary` 존재, `status` required)을 검사하고 어긋나면
`RoleBundleError`로 기동을 막는다. 이 role에서 `NEED_REPLAN`을 쓸 일이 없더라도 enum에는
있어야 한다.

`answer`는 Slack 본문에 그대로 들어간다. 문항의 `stem`/`options`와 같은 mrkdwn 규칙을
따른다 — 굵게는 별 하나, 표·헤더·링크 문법 금지. 매체 문법을 확인하지 않고 쓰면 강조가
`**날문자**`로 찍힌다 (lessons C12).

### 인용 대조 — 출제와 같은 기계 검사, 다른 처분

`citations`는 `verify_citations`를 **그대로 재사용해** 대조한다. 하네스가 파일을 열어 그 줄
범위에 그 문장이 실재하는지 확인한다. LLM 판단이 아니다.

처분은 출제와 다르다. 출제에서 대조 실패는 문항 폐기지만, 여기서는 **답변 폐기 사유가
아니다.** 틀린 인용만 떼고 본문은 낸다. 대신 뗐다는 사실을 한 줄로 적는다:

> _근거 1건은 대조에 실패해 제외했습니다_

조용히 지우면 lessons C12에서 겪은 "고친 것이 새 거짓말이 되는" 자리가 된다. 화면이 바뀌었으면
바뀌었다고 화면에 적는다.

### 길이

Slack 텍스트 상한을 넘으면 자르고 잘렸다고 표시한다.

## 흐름

질문은 두 경로로 들어온다. **둘 다 같은 진입점으로 모은다.**

- `message` — 스레드에 그냥 답글을 단 경우
- `app_mention` — 스레드 안에서 `@tutor`를 붙여 물은 경우

지금 `on_mention`은 이미 세션이 있는 스레드를 조용히 무시한다(중복 회차 방지). 채점이 끝난
스레드에서의 멘션은 **새 회차 요청이 아니라 질문**이므로 `on_question`으로 넘긴다. 이걸
빠뜨리면 "@tutor 이거 왜 이래?"가 아무 반응 없이 사라진다 — 사용자가 가장 자연스럽게
시도할 형태다.

```
message / app_mention 이벤트
  ├─ bot_id 있거나 subtype 붙음      → 버린다 (루프 차단)
  ├─ 스레드에 회차 없음               → 무시
  ├─ 회차 진행 중 (done=False)        → "채점 후에 물어봐 주세요"
  ├─ owner 아님                       → 답하지 않는다
  ├─ TTL 만료                         → "회차가 만료됐습니다"
  └─ 통과
       → lock (잡혀 있으면 "답변 준비 중" 안내)
       → status "답변 준비 중…"
       → 세션 없으면 start_worker(회차 컨텍스트)  ← output_schema 강제, 위 §세션 모델
         있으면          adapter.send(sid, fence(질문))
       → wait_for(위 둘을 한 코루틴으로, TURN_TIMEOUT)
       → 인용 대조 → 게시(스레드 안) → trace 기록
```

### 루프 차단은 선택이 아니다

`message.channels` 구독은 스레드 답글도 배달하므로, 봇이 스레드에 단 답변이 다시 `message`
이벤트로 돌아온다. `bot_id`가 있거나 `subtype`이 붙은 메시지를 진입 전에 버리지 않으면 봇이
자기 답변에 답하는 무한 루프가 된다. 이건 회귀 테스트로 고정한다.

### 타임아웃은 세션 전체를 감싼다

`start_worker`와 `send`를 한 코루틴으로 묶어 `TURN_TIMEOUT`을 건다. 실제 작업(repo 읽기)은
첫 turn에서 일어나므로 `send`에만 상한을 걸면 매달리는 쪽이 무방비다 — 2026-08-24에 이
정확한 실수로 `@tutor`가 통째로 멎었다 (lessons C14).

## 실패 처리

전부 스레드에 사실대로 말한다. 조용히 삼키면 사용자도 우리도 원인을 못 찾는다.

| 상황 | 동작 |
|---|---|
| 세션 실패·타임아웃 | `💥 답변에 실패했습니다: {타입}` — 같은 질문을 다시 물으면 된다 |
| 메모리 세션 없음 | trace로 회차 복원 후 새 세션 |
| 복원 실패 (회차가 없는 스레드) | **조용히 무시한다** — 아래 참고 |
| TTL 만료 | `⚠️ 회차가 만료됐습니다` — **회차당 한 번만**. 게이트가 없으면 그 스레드의 모든 답글(남의 답글 포함)마다 채널로 브로드캐스트된다 |
| repo가 레지스트리에 없음 | 답하지 않고 사유를 말한다 — 빈 경로는 하네스 자기 repo를 읽는 것이 된다 |
| 답변이 상한 초과 | 자르고 잘렸다고 표시 |

**회차가 없는 스레드에서는 아무 말도 하지 않는다.** tutor 봇이 있는 채널의 모든 스레드
답글이 이 경로로 들어오므로, "이 회차를 찾지 못했습니다"를 보내면 봇과 무관한 대화마다
끼어들게 된다. 안내가 필요한 것은 **회차가 있는데 쓸 수 없는 경우**(진행 중·owner 아님·
만료)뿐이다.

| `src/devcrew/slack_tutor.py` | `on_question` 진입점, 회차 복원 |
| `src/devcrew/slack_engine.py` | `message` 핸들러 배선 (`make_tutor_say` 재사용) |

**Role 추가는 테이블 다섯 곳을 함께 채운다** — `Role` enum, `enforcement._POLICIES`,
`harness.yaml`의 `roleDefaults`와 `roleBudgets`, 그리고 `orchestrator.BUNDLED_ROLES`.
다섯 번째를 빠뜨리면 `spawn`이 role bundle 버전 stamp를 건너뛰고 `start_worker`가
`RoleBundleError`를 던진다. lessons C10이 "새 Role을 추가하고 정책 테이블을 빠뜨림"으로
이미 기록한 자리다.

| 1 | 진행 중 스레드의 자유 답글 → 답변 없이 안내만 | 정답 유출 경계 |

잃었다 (lessons C1).

## 범위 밖

- **진행 중 질문** — 정답 유출 경계 때문에 의도적으로 제외. 필요해지면 컨텍스트 차단을 별건으로
- **과거 Q&A replay** — 재시작 후 대화 복원. 회차 맥락으로 충분하다
- **Q&A를 리포트에 싣기** — trace에는 남지만 HTML 리포트에는 넣지 않는다
- **오답 노트 연동** — 질문했다는 사실이 노트에 영향을 주지 않는다. 노트의 축은 정오뿐이다
- **repo 전반 질문** — 회차 문항에서 출발하지 않는 질문은 이 기능의 대상이 아니다.
  막지는 않되 프롬프트가 회차로 되돌린다
